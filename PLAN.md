# Dockit — Architecture & Implementation (Final)

## Project Overview

A local documentation hub web application ("Context7-like") that supports multiple documentation source types and normalizes them into a unified, searchable HTML bundle for LLM context. Built with React + TypeScript (frontend) and Node.js 24 (backend).

## 2. Data Model (SQLite)

### Tables

**entries**
| Column       | Type    | Notes                                    |
|-------------|---------|------------------------------------------|
| id          | TEXT PK | UUID (generated by backend)              |
| name        | TEXT    | Display name                             |
| version     | TEXT    | Version string                           |
| description | TEXT    | Optional description                     |
| status      | TEXT    | pending / building / ready / error       |
| created_at  | TEXT    | ISO timestamp                            |
| updated_at  | TEXT    | ISO timestamp                            |

**sources**
| Column     | Type    | Notes                                              |
|------------|---------|----------------------------------------------------|
| id         | TEXT PK | UUID                                               |
| entry_id   | TEXT FK | References entries.id with ON DELETE CASCADE       |
| type       | TEXT    | One of: zip, antora, maven                         |
| label      | TEXT    | User-friendly label                                |
| config     | TEXT    | JSON string — shape depends on type                |
| status     | TEXT    | pending / building / ready / error                 |
| created_at | TEXT    | ISO timestamp                                      |

**builds**
| Column       | Type    | Notes                        |
|--------------|---------|------------------------------|
| id           | TEXT PK | UUID                         |
| entry_id     | TEXT FK | References entries.id        |
| status       | TEXT    | pending / building / ready / error |
| log          | TEXT    | Build output log             |
| started_at   | TEXT    | ISO timestamp                |
| finished_at  | TEXT    | ISO timestamp                |

### Source Config Shapes (stored as JSON text in `sources.config`)

```typescript
interface ZipSourceConfig {
  url?: string;
  localPath?: string;       // pre-downloaded .zip file
}

interface AntoraSourceConfig {
  repoUrl?: string;
  zipPath?: string;
  localPath?: string;        // pre-cloned local directory
  playbookOverrides?: Record<string, unknown>;
}

interface MavenSourceConfig {
  groupId: string;
  artifactId: string;
  version: string;
  classifier?: string;       // defaults to "javadoc"
  useMavenCommand?: boolean; // use mvn dependency:copy (settings.xml)
  localJar?: string;         // pre-downloaded .jar file
}

interface AsciidocSourceConfig {
  repoUrl?: string;
  zipPath?: string;
  localPath?: string;        // pre-cloned local directory
  sourcePath?: string;       // subdirectory where .adoc files live
}
```

### Config Parsing

The `config` column stores JSON text. On read, helper functions `getSources(entryId)` and `getSource(id)` in `db/index.ts` parse the JSON into typed objects automatically.

## 3. API Endpoints

| Method | Path | Purpose | Notes |
|--------|------|---------|-------|
| `GET`    | `/api/entries`                          | List entries + source counts | LEFT JOIN sources for count |
| `POST`   | `/api/entries`                          | Create entry | Requires name + version |
| `GET`    | `/api/entries/:id`                      | Get entry + parsed sources + latest build | Config JSON is parsed |
| `PUT`    | `/api/entries/:id`                      | Update entry metadata | Partial update supported |
| `DELETE` | `/api/entries/:id`                      | Delete entry + cascaded sources/builds | CASCADE on FK |
| `POST`   | `/api/entries/:id/sources`              | Add source (needs entryId in route) | Validates config by type |
| `PUT`    | `/api/sources/:id`                      | Edit source (flat route) | `sources-flat.ts` router |
| `DELETE` | `/api/sources/:id`                      | Remove source (flat route) | `sources-flat.ts` router |
| `POST`   | `/api/entries/:id/build`                | Trigger async build | Returns 202 + buildId |
| `GET`    | `/api/entries/:id/build-status`         | Poll latest build status | Returns status + log |
| `GET`    | `/api/entries/:id/cli-script`           | Download .sh script | Content-Disposition attachment |
| `GET`    | `/api/entries/:id/search?q=term`        | Keyword search index.json | Scored by term frequency |
| `GET`    | `/api/bundle/:entryId/*`                | Serve bundled HTML files | Used by DocViewer iframe |

### Route Architecture

Sources are served via two routers:
- `sources.ts` (with `mergeParams: true`) mounted at `/api/entries/:entryId/sources` — handles POST (needs the parent `:entryId` param)
- `sources-flat.ts` mounted at `/api/sources` — handles PUT and DELETE via direct source ID lookup (no entryId needed)

## 4. Processing Pipeline (Build)

Executed when user clicks "Build Now" or the CLI script is downloaded:

```
For each source attached to entry:

  ZIP source:
    → If localPath: Extract pre-downloaded .zip via unzipper
    → If url: fetch(url) → pipe to unzipper.Extract → data/{entryId}/sources/{sourceId}/

  Maven source:
    → If localJar: Extract pre-downloaded .jar via unzipper
    → If useMavenCommand: spawn mvn dependency:copy (uses ~/.m2/settings.xml)
    → Else: HTTP download from Maven Central + unzipper.Extract

  AsciiDoc source:
    → If localPath: Use directory as-is (no clone, no cleanup)
    → If repoUrl: Clone git repo to tmpdir
    → If zipPath: Extract ZIP to tmpdir
    → Scan for .adoc files (optionally limited to sourcePath)
    → convertFile() via @asciidoctor/core API → HTML files in sources/{sourceId}/

  Antora source:
    → If localPath: Use directory as content source directly
    → If repoUrl: Clone git repo to content dir
    → If zipPath: Extract ZIP to content dir
    → Generate antora-playbook.yml pointing to content source
    → spawn('npx', ['antora', playbookPath])
    → Output lands in data/{entryId}/antora/{sourceId}/output/

Normalizer:
    → Walk all source directories
    → Copy *.html (and all other files) into data/{entryId}/bundle/
    → Flatten under source label subdirectory

Indexer (node-html-parser):
    → Parse each HTML file in bundle/
    → Extract: title (<title> or first <h1>), headings (<h1>-<h4>), text snippet (first 300 chars)
    → Write data/{entryId}/index.json as JSON array

Search:
    → Load index.json
    → Split query into terms, score by term frequency in title+headings+snippet
    → Title matches get score bonus
```

### Build Log Update Mechanism

- A `Map<string, string[]>` stores in-memory log lines keyed by `buildId`
- The `log()` callback is passed to each service step
- On build completion (or error), all lines are concatenated and persisted to `builds.log`
- During a build, polling `/build-status` returns the latest accumulated log
- Many simultaneous builds are possible as they're tracked per buildId in memory

## 6. Execute Button — Dual Mode

### "Build Now" (primary button)

1. `POST /api/entries/:id/build` → backend sets entry + sources status to `building`, inserts `builds` row
2. Returns 202 immediately with `{ buildId, status: 'building' }`
3. Frontend starts polling `GET /api/entries/:id/build-status` every 1500ms
4. BuildPanel displays live log output during build
5. On completion (`ready` or `error`), polling stops, status chips update

### "Download Script" (outline button)

1. `GET /api/entries/:id/cli-script` → backend generates a `.sh` shell script
2. For each source, script includes the appropriate `curl`/`git clone`/`unzip` commands
3. Script is returned with `Content-Disposition: attachment` header
4. Frontend creates a Blob download from the script text
5. User can inspect, modify, and run the script locally

## 9. MCP Server Architecture

The MCP server (`src/mcp.ts`) is a separate entry point in the server package that exposes Dockit functionality as tools for AI assistants (Claude Desktop, Cline, etc.).

### Transport

Uses **stdio** transport (`StdioServerTransport`) — the standard MCP protocol over stdin/stdout. When the AI host launches the process, it sends JSON-RPC requests on stdin and reads responses from stdout.

### Startup Flow

1. Load `dockit.yaml` from project root (or CWD)
2. Validate config (entries, sources, required fields)
3. Upsert entries and sources into SQLite (`INSERT OR REPLACE`)
4. Optionally auto-build all entries if `mcp.autoBuild: true`
5. Register 5 tools with input schemas
6. Connect `StdioServerTransport` — server ready

### Shared Services (MCP + REST)

Both `mcp.ts` and `routes/build.ts` use the same extracted services:

| Service | Used By | Purpose |
|---------|---------|---------|
| `buildPipeline.ts` | REST build route, MCP `dockit_build` | Entry build orchestration |
| `indexer.ts` | REST search, MCP `dockit_search` | Index building + keyword search |
| `configLoader.ts` | MCP startup | YAML → DB sync |
| `textExtractor.ts` | MCP `dockit_get_doc` | HTML → plain text for LLM |
| `paths.ts` | All | Shared DATA_ROOT resolution |

### Tool Implementations

| Tool | Implementation |
|------|---------------|
| `dockit_list_entries` | `SELECT` from entries table, count sources |
| `dockit_search` | `searchIndex()` → in-memory JSON index, term frequency scoring |
| `dockit_get_doc` | Read HTML from bundle, `extractTextFromHtml()`, truncate at 50KB |
| `dockit_build` | `buildEntry()` (fire-and-forget) |
| `dockit_build_status` | `SELECT` latest build record, return status + last 2000 chars of log |

### Tool Name Prefix

Configurable via `mcp.toolPrefix` in `dockit.yaml`. Default: `dockit_`. Allows renaming to avoid conflicts with other MCP servers.

## 10. Local/Offline Mode

Every source type supports an alternative local path that takes precedence over remote URLs. Validated at build time (not config sync), so files can be mounted later (Docker volumes, network shares).

### Config Field Summary

| Type | Local Field | Behavior |
|------|-------------|----------|
| ZIP | `localPath` | Extracts pre-downloaded .zip via unzipper |
| Maven | `useMavenCommand` | Spawns `mvn dependency:copy` via `~/.m2/settings.xml` |
| Maven | `localJar` | Extracts pre-downloaded .jar via unzipper |
| Antora | `localPath` | Uses pre-cloned directory as Antora content source |
| AsciiDoc | `localPath` | Uses pre-cloned directory (no cleanup, read-only) |

### Maven CLI Details

Spawns: `mvn org.apache.maven.plugins:maven-dependency-plugin:3.10.0:copy -Dartifact=g:a:v:jar:classifier -DoutputDirectory=targetDir -Dtransitive=false`

Respects `~/.m2/settings.xml` for:
- Proxy configuration (`<proxies>`)
- Mirror settings (`<mirrors>`)
- Private repository credentials (`<servers>`)

### Cleanup Policy

- **Remote sources** (git clone, ZIP extract): temp directories cleaned up after build
- **Local sources** (`localPath`): directories are read-only, never modified or deleted
- **Antora work dirs**: Inside `data/` — overwritten on each build, no manual cleanup needed

### UI Toggles (SourceForm)

Each source type has radio button toggles:
- **ZIP**: Remote URL / Local File
- **Maven**: Direct Download / Maven CLI / Local JAR
- **Antora**: Git Repo / Local Dir / ZIP File
- **AsciiDoc**: Git Repo / Local Dir / ZIP File

## 11. Design Decisions & Deviations from Original Plan

1. **`paths.ts`**: Added a shared module for `DATA_ROOT` resolution. The original plan used relative paths via `process.cwd()` which was fragile across subdirectories. The shared module uses `import.meta.url` → `__dirname` → relative path resolution.

2. **`sources-flat.ts`**: Original plan had sources PUT/DELETE mounted at `/api/entries/:entryId/sources/:sourceId`. The frontend API client uses flat routes `/api/sources/:id` for simplicity. A separate router handles these.

3. **`getSources()` / `getSource()`**: The `config` column stores JSON text. Helper functions in `db/index.ts` parse configs on read, avoiding manual `JSON.parse()` at every call site.

4. **`node-html-parser` over Cheerio**: Cheerio 1.x pulls in `undici` which requires Node 20+. `node-html-parser` has zero server-side deps.

5. **Antora via CLI**: The original plan used `@antora/site-generator` programmatic API. Implemented via `npx antora` child process for better compatibility and error handling.

6. **No separate `hooks/` or `ui/` directories**: Components are self-contained and state is managed inline with `useState`/`useEffect` + the API client module. No UI primitives library was needed — all styling is via Tailwind utility classes.

7. **Tailwind CSS 4**: Uses the new `@import "tailwindcss"` and `@theme` directive instead of `tailwind.config.js`. The `@tailwindcss/vite` plugin handles compilation.

8. **Build log buffering**: Uses an in-memory `Map<buildId, string[]>` for live log streaming during builds. This avoids filesystem overhead and supports concurrent builds. Log is persisted to DB on completion.

9. **AsciiDoc source type**: Added as a fourth source type (after ZIP, Maven, Antora). Clones a Git repo, discovers `.adoc` files, and converts them to HTML via `@asciidoctor/core`. An optional `sourcePath` field limits the scan to a specific subdirectory (e.g. `docs/src/main/asciidoc` for Quarkus). This was added to handle real-world projects like Quarkus that use Asciidoctor directly rather than Antora.

10. **MCP server in same package**: The MCP stdio server lives in `apps/server` as a separate entry point (`mcp.ts`), sharing all services, types, and DB access. This avoids duplication — both the REST API and MCP tools use the same `buildEntry()`, `searchIndex()`, and DB helpers.

11. **YAML-first config for MCP**: Entries and sources can be defined entirely in `dockit.yaml`. On startup, the MCP server upserts them into SQLite. The web UI and API can still be used for ad-hoc entries, but the YAML config is the canonical source for MCP-driven workflows.

12. **Plain text extraction for LLM**: `dockit_get_doc` returns HTML content as plain text (stripped tags, markdown-style headings). This wastes fewer tokens than raw HTML. Content is truncated at 50KB with a paragraph-aware boundary.

13. **`localPath` consistency**: The same field name `localPath` is used for ZIP (file), Antora (directory), and AsciiDoc (directory) sources. Validated at build time to avoid tight coupling with config sync timing.

14. **Maven dependency plugin 3.10.0**: Hardcoded plugin version. Prevents issues with incompatible defaults across Maven installations. Uses `maven-dependency-plugin` which is bundled with Maven — no extra installation needed.

15. **AsciiDoc API over CLI**: Switched from spawning `npx asciidoctor @filelist.txt` (which the JS CLI doesn't support) to calling `asciidoctor.convertFile()` via `@asciidoctor/core` API directly. Handles 312+ files reliably and reports per-file errors.
